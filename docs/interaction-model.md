# Modeling a screen interaction

Use this branch of `model-product` for a task someone wants to try on example screens. One person describes, corrects and confirms the flow in the same chat.

1. **Choose the boundary before modeling.** Ask whether to cover the whole agreed product or one named workflow, capability, scenario or use case. Reuse an explicit choice from the brief. Name the boundary in product terms. For whole-product coverage, enumerate all agreed capabilities with the modeler. For a workflow, enumerate the tasks inside it.
2. **Agree on the scenario inventory before drafting screens.** From the brief and discovery decisions, propose a short list in product language. Give each scenario a stable ID, the capability it covers, who is trying to do what, the situation that starts it and the observable outcome. Walk through a recent real example with the modeler. Ask what other outcomes matter in this scope, including abandoning a task, recovering from an error or returning to earlier work when relevant. Check each in-scope capability against the list. Mark exclusions and unresolved scope questions explicitly. Ask “For this scope, which use cases are missing, should change, or can we use this list to start modeling?” Wait for the modeler's answer and record the agreed inventory in the workspace. On resume, reuse the agreed inventory and review changes.
3. **Review the data model when the scenarios depend on information.** After the scenario inventory is agreed, propose the things people work with, the facts each scenario needs about them, and how they relate. Use product language. Walk one example through its lifecycle: who supplies each fact, when it becomes available, where someone needs to see it, and what may change. Distinguish sourced facts from proposals. Ask what is missing or should change and obtain explicit agreement before using the model to design screens. Record the reviewed proposal and its confirmation with the scenario IDs and evidence. If the scenarios need no meaningful data model, briefly record why and proceed. Revisit affected mappings when the model changes.
4. **Map the agreed scenarios to screens.** Carry the inventory into the Markdown, keeping the IDs when mapping scenarios to starting screens, actions and destinations. For each scenario, check that the proposed screens show or collect the agreed facts at the step where they are needed. Surface any missing fact, including one absent from an otherwise navigable screen. Show any scenario still lacking a route as an open gap in the Markdown. Write `interaction-model.md` beside the workspace ledger, with scope, example content and routes in one fenced YAML block. Cite the discovery revision, evidence and decisions in surrounding prose. Follow the [worked example](../examples/interaction-model/interaction-model.md) and [format schema](../schemas/interaction-model.schema.json).
5. **Review coverage together.** Render the file with the command below. Share the local preview, expand **Review coverage**, and inspect the inventory and each capability's start, actions and destinations. Ask “Which screens or routes are missing for this scope? From the last screen of each task, where do you need to go next?” A missing scenario step stops that trace at the gap. If replay reveals a new use case, revisit the inventory with the modeler, update its scope and mappings, then replay the affected scenario. Record newly discovered gaps and decisions using the shared workspace workflow.
6. **Try and correct.** Let the modeler pick a scenario and select **Start**. The viewer shows one action at a time. Invite feedback at the end of the scenario or when something feels wrong. Avoid asking for a chat reply after each click. At any point they can describe a correction in chat. Update the Markdown, regenerate the viewer and give them the printed link to the changed source screen using `--start SCREEN_ID`. A click on the original action now tests the new destination with the same example content. Supply a fresh preview filename for each correction so an open tab cannot show an old revision.
7. **Confirm this version.** After inventory review and scenario replay, ask whether the screens and navigation cover the chosen scope. Silence, opening the viewer and completing a replay all leave the model pending. Record only an explicit answer from this modeler as evidence, identifying scope and the model revision digest printed by the command. Preserve earlier confirmation history. On resume, compare the current digest to the reviewed digest. After a confirmed model changes, mark the current version pending, return to the changed screen and have the modeler retry the changed action. Then let them confirm immediately or choose additional replay first. Never require a second reviewer.
8. **Hand off** the single corrected Markdown file. The receiving viewer regenerates all screens and links from that file alone.

From the repository root, run the following with a model and output path of your choice. Open the printed link in a current browser. Omit `--start` to begin with the scenario list.

```sh
.venv/bin/python -m src.adp_discovery interaction-view examples/interaction-model/interaction-model.md /tmp/decision-review.html --start review-form
```

Text fields start read-only. To model editing, give a field a stable `bind` ID, reuse it on its display paragraphs and action rows, and mark the saving action with `commit: true`. Saved values last until the preview reloads. Actions belong to their source screen. Scenario step IDs resolve there in order. An unknown declared destination is invalid. A missing intended step remains visible for review. The generated preview is disposable. Confirmation evidence belongs in working state and refers to the exact Markdown revision.

The scenario list shows completion and lets the modeler resume an interrupted route. Use the same Markdown source path for corrections to preserve unaffected progress in browsers that share local storage across the preview files. For browsers that isolate local files, regenerate and reload the same preview URL.

The modeler can keep Notes beside each scenario or on a guided screen. After replay, use **Back to scenarios** and **Copy notes** to bring the feedback into chat together. Screen notes carry the screen and step. Notes are stored in the browser for the reviewed model revision.
